# Daily Codeforces Spin Streak: Project Guide

Study notes for the Mobile Computing lab evaluation: setup, architecture, the important functions,
viva questions and practice modification tasks.

---

## 1. Project setup

1. Install **Xcode** (iOS 18 SDK or newer) on a Mac.
2. Clone the repository:
   ```bash
   git clone https://github.com/ShahariarEmon112/DailyCFSpinStreak_MobileComputing.git
   ```
3. Open `DailyCFSpinStreak.xcodeproj`.
4. Copy your `GoogleService-Info.plist` into the `DailyCFSpinStreak/` source folder (next to
   `ContentView.swift`). It is **git-ignored**, so it is never pushed to GitHub.
5. Wait for Xcode to finish resolving the Swift packages (Firebase). If it fails:
   **File → Packages → Reset Package Caches**.
6. Pick an iPhone simulator (iOS 18+) and press **⌘R**.

## 2. Firebase configuration

1. [console.firebase.google.com](https://console.firebase.google.com) → your project.
2. **Project settings → Your apps → iOS app.** Its bundle ID must be `com.example.DailyCFSpinStreak`
   (the same as Xcode → target → Signing & Capabilities). Download `GoogleService-Info.plist` from here.
3. **Authentication → Sign-in method → Email/Password → Enable.**
4. **Firestore Database → Create database** (any region).
5. **Firestore → Rules:** paste [`../firestore.rules`](../firestore.rules) and click **Publish**:
   ```
   match /users/{userId}/{document=**} {
     allow read, write: if request.auth != null && request.auth.uid == userId;
   }
   ```
   Each logged-in user can only read and write their own data.

| Setting | Value |

## 4. Architecture (MVVM)

```
 View (SwiftUI)  ──calls──▶  ViewModel (ObservableObject)  ──calls──▶  Service
      ▲                            │ @Published                        │
      └──────── redraws ◀──────────┘                                   ▼
                                                    Firebase  /  Codeforces API
```

- **Model:** plain data structs (`Problem`, `AppUser`, `SolveHistory`, `Submission`, `UserStats`).
  They are `Codable`, so the same struct is decoded from Codeforces JSON *and* saved to Firestore.
- **View:** shows data and forwards taps to the ViewModel. Views contain no networking.
- **ViewModel:** holds screen state (`@Published`), validates input and calls services.
- **Service:** the only code that talks to the outside world.
  - `FirebaseService`: Auth and Firestore CRUD
  - `CodeforcesAPIService`: URLSession and JSON decoding
  - `StreakService`: pure streak math (no network)

### Who owns which ViewModel

| ViewModel | Created (`@StateObject`) in | Lives while | Passed down as |
|---|---|---|---|
| `AuthenticationViewModel` | `ContentView` | app is running | `@ObservedObject` |
| `ProblemViewModel`, `TimerViewModel`, `StatisticsViewModel` | `MainTabView` | user is logged in | `@ObservedObject` |

Because `TimerViewModel` is owned by `MainTabView`, not by the problem screen, the timer is **not
reset** when the user switches tabs or goes back.

### Firestore data

```
users/{uid}
    id, name, email, cfHandle, currentStreak, longestStreak,
    verifiedDays: ["2026-11-11", "2026-11-12", "2026-11-13"], createdAt
users/{uid}/history/{problemId}      ← doc id "1520A" ⇒ one entry per problem
    problem{…}, durationSeconds, hintUsed, status (attempted|finished|verified),
    attemptedAt, verifiedAt
users/{uid}/retry/{problemId}
    contestId, index, name, rating, tags, addedAt
```

### Main flows

**Spin.** `SpinView` → `ProblemViewModel.spin(seenProblemIds:)`:
1. `CodeforcesAPIService.fetchProblems()` downloads `problemset.problems` the first time, then uses the cache.
2. The list is filtered by rating range (unrated problems are skipped) and by selected tags (the problem must have all of them).
3. Problems already in history, already Accepted on the user's handle, or currently shown are removed.
4. `randomElement()` picks one. If nothing fresh is left, a repeat is allowed and an info message is shown.

**Solve.** `ProblemDetailView`:
- `onAppear` calls `timerVM.prepare(for:)`, which resets the timer only if this is a different problem.
- Start, Pause, Resume and Finish call `TimerViewModel`.
- `onDisappear` and `scenePhase == .background` pause the timer automatically and save an *attempted* entry.
- **Show Hint** sets `hintUsed = true`, the tags appear, and the solve is marked hint-assisted.
- **Finish** saves a `finished` entry, which never changes the streak.

**Verify.** `StatisticsViewModel.verifySolve(...)`:
1. A Codeforces handle is required.
2. If this problem is already `verified`, the function stops (duplicate protection).
3. It downloads `user.status?handle=…`.
4. It keeps submissions with the same `contestId` and `index` and `verdict == "OK"`.
5. The earliest Accepted submission's `creationTimeSeconds` becomes the solve date.
6. The history entry is saved as `verified`.
7. The local `dayKey` ("yyyy-MM-dd") is added to `verifiedDays` only if it is missing, and both streaks are recalculated.
8. `users/{uid}` is updated, and `authVM.currentUser` is updated so the Dashboard redraws.

**Streak decay.** Each time the Dashboard appears and after login, `refreshStreak()` recalculates
`currentStreak` from `verifiedDays`. A missed day therefore resets it to 0.

## 7. Viva questions with short answers

1. **What is MVVM and why did you use it?**
   Model–View–ViewModel. Views only display data; ViewModels hold state and logic; Models are plain
   data. It keeps the UI simple and the logic easy to test and change.

2. **Difference between `@State` and `@StateObject`?**
   `@State` stores a simple value type owned by the view. `@StateObject` creates and owns a
   reference-type `ObservableObject` and keeps it alive across view redraws.

3. **Difference between `@StateObject` and `@ObservedObject`?**
   `@StateObject` *creates and owns* the object. `@ObservedObject` only *watches* an object created
   somewhere else. If you used `@ObservedObject` to create it, the object could be recreated on
   every redraw.

4. **What does `@Published` do?**
   It notifies observing views whenever the property changes, so SwiftUI redraws them.

5. **What is `@Binding`? Give an example.**
   A two-way reference to state owned by another view. `DashboardView` gets `$selectedTab` and
   changes the tab owned by `MainTabView`.

6. **Why does the timer not reset when you change tabs?**
   `TimerViewModel` is a `@StateObject` in `MainTabView`, which stays alive while logged in. The
   problem screen only observes it.

7. **How do you measure time accurately?**
   The app stores `accumulatedSeconds` and the `runningSince` date, and computes
   `accumulated + (now − runningSince)`. The one-second loop only refreshes the label, so missed
   ticks don't cause wrong time.

8. **What happens when the app goes to the background?**
   `scenePhase` changes to `.background`. `ProblemDetailView` then pauses the timer, shows the
   reason, and saves an "attempted" entry.

9. **Why open the problem with `SFSafariViewController` instead of Safari?**
   The app stays in the foreground, so the timer keeps running while the user reads the statement.

10. **How does session persistence work?**
    Firebase Auth stores the login on the device. On launch, `restoreSession()` checks
    `Auth.auth().currentUser` and loads the profile, so the Login screen is skipped.

11. **What is `Codable`?**
    `Encodable` + `Decodable`. Swift generates code to convert between structs and JSON (or
    Firestore documents) when the property names match the keys.

12. **Why are `rating` and `tags` optional?**
    Some Codeforces problems are unrated, and optionals stop decoding from failing when a key is
    missing.

13. **What is `CodeforcesResponse<T>`?**
    A generic wrapper for the API "envelope" `{status, comment, result}`. `T` is the result type
    (`ProblemsetResult`, `[Submission]`, `[CodeforcesUser]`).

14. **How do you handle an invalid handle?**
    `user.info` returns `status: "FAILED"` with a comment, which becomes `CodeforcesError.apiFailed`.
    The user sees "Codeforces handle not found", and nothing is saved.

15. **How do you verify a solve?**
    The app downloads `user.status`, keeps submissions with the same contestId and index and
    `verdict == "OK"`, and takes the earliest one. Only then is the entry marked `verified` and the
    streak updated.

16. **Why doesn't the Finish button increase the streak?**
    Pressing a button proves nothing. Only an Accepted verdict from the Codeforces API is trusted.

17. **How do you prevent duplicate counting?**
    The history document id is the problem id, and verification stops if it is already `verified`.
    `verifiedDays` stores each date only once, so several solves on one day count as one streak day.

18. **How is the solve date decided, and which time zone is used?**
    From the submission's `creationTimeSeconds`, converted to a "yyyy-MM-dd" key in the user's
    **local** time zone (`StreakService.dayKey`).

19. **How is the current streak calculated?**
    Start at today (or yesterday, if today isn't solved yet) and walk back one day at a time while
    each day is in `verifiedDays`.

20. **What is async/await? Why use `Task { }` in buttons?**
    It lets the app wait for network work without blocking the UI. Button actions are not async, so
    `Task { await … }` starts an async context.

21. **What does `defer` do in your ViewModels?**
    It runs when the function exits (success *or* error), so `isLoading = false` always happens and
    the spinner never gets stuck.

22. **Where do you use the delegate pattern?**
    `AppDelegate` conforms to `UIApplicationDelegate`. iOS calls its
    `didFinishLaunchingWithOptions` method, where Firebase is configured. SwiftUI connects it with
    `@UIApplicationDelegateAdaptor`.

23. **How does swipe-to-delete work?**
    `ForEach(...).onDelete(perform: problemVM.removeFromRetryList)`. SwiftUI passes an `IndexSet`;
    the row is removed locally and the Firestore document is deleted.

24. **How do you keep Firebase credentials out of GitHub?**
    `GoogleService-Info.plist` is listed in `.gitignore`. Firestore security rules also make sure
    each user can only access their own data.

25. **Why is JSON decoded with `Task.detached`?**
    The problem set is several MB. Decoding it off the main thread keeps the UI smooth.

26. **Why are the models marked `nonisolated`?**
    The project runs code on the MainActor by default. Models are plain data, so `nonisolated` lets
    them be decoded on background threads (`Task.detached`, Firestore).

## 8. Practice modification tasks

### Task 1: Add a "Clear filters" / reset button for the rating range
- **Where:** `ProblemViewModel` and `SpinView.ratingCard`.
- **How:** add `func resetFilters() { minRating = 800; maxRating = 1400; selectedTags = [] }`, then put
  `Button("Reset") { problemVM.resetFilters() }` in the rating card header.

### Task 2: Add a new topic tag (for example "geometry")
- **Where:** `ProblemViewModel.availableTags`.
- **How:** append `"geometry"`. It must be the exact Codeforces tag name. The grid in `SpinView`
  uses `ForEach` over the array, so the chip appears automatically.

### Task 3: Show the user's Codeforces rating on the Profile screen
- **Where:** `AuthenticationViewModel`, `ProfileView`.
- **How:** add `@Published var cfRating: Int?`. In `connectHandle`, after `fetchUser`, set
  `cfRating = codeforcesUser.rating`. In `ProfileView`, add
  `LabeledContent("Rating", value: authVM.cfRating.map(String.init) ?? "Unrated")`.
  `CodeforcesUser.rating` is already decoded.

### Task 4: Allow deleting history entries with swipe-to-delete
- **Where:** `FirebaseService`, `StatisticsViewModel`, `HistoryView`.
- **How:**
  1. In `FirebaseService`: `func deleteHistory(uid: String, problemId: String) async throws { try await historyCollection(uid).document(problemId).delete() }`.
  2. In `StatisticsViewModel`: add `removeHistory(at offsets: IndexSet)`, copying the pattern of
     `ProblemViewModel.removeFromRetryList(at:)`.
  3. In `HistoryView`: add `.onDelete(perform: statsVM.removeHistory)` to the `ForEach`.

  Note: deleting a verified entry should **not** remove the day from `verifiedDays`, because the
  Accepted submission still exists.

### Task 5: Add a daily goal (for example, 2 verified problems per day)
- **Where:** `StatisticsViewModel`, `DashboardView`.
- **How:** add
  `var verifiedTodayCount: Int { history.filter { $0.status == .verified && $0.verifiedAt.map(Calendar.current.isDateInToday) == true }.count }`.
  On the Dashboard, show `StatCard(title: "Today's Goal", value: "\(statsVM.verifiedTodayCount)/2", …)`
  and add a `ProgressView(value: Double(count), total: 2)`.

### Bonus ideas
- **Change the theme color:** edit `Theme.primary` in `Theme.swift`, and every screen updates.
- **Add a "Skip" button that spins again:** call `problemVM.spin(seenProblemIds:)` from `ProblemCard`'s screen.
- **Sort history by rating:** `statsVM.history.sorted { ($0.problem.rating ?? 0) > ($1.problem.rating ?? 0) }` in the `ForEach`.
